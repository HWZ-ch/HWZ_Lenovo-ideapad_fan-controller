# 逆向笔记：联想小新 16 IRL8 风扇控制

本文记录从「想给风扇满速」到「确认唯一可行通道」的完整过程，**包括走过的弯路**，避免后来者重复踩坑。

机型：**联想小新 16 IRL8**（Lenovo EM 机型，驱动 `AcpiVpc.sys`）。系统 Windows 11。

---

## 一、目标

联想电脑管家有个「降温除尘」：风扇全速转约 9 秒、停约 2 秒，循环约 2 分钟后自动复位。
想把它变成可一键开关、可脚本化的持续状态。

---

## 二、走过的弯路（已证伪，勿再尝试）

### 1. 写 EC 寄存器 `0xFE` —— 假阳性

社区流传「小新系列风扇受 EC 寄存器 `0xFE` 控制，写 `0x50` 即满速」。**在本机不成立。**

当时的「验证」有缺陷：写入后热区温度轻微下降、用户说「听到了」。后来发现**当时后台正跑着联想除尘命令**，声音是那条命令的，被误归因了。

正确的验证方式——在**触发联想真正除尘（风扇必然在转）时**扫描 EC 全部 256 个寄存器：

```
结果：0xFE 始终为 0x00
```

即 `0xFE` 与风扇状态**完全无关**。单独写 `0xFE=0x50` 时，热区仅微降、用户听不到风扇转。

**结论：本机不存在可被直接写入的「风扇转速寄存器」。** 直写 EC 这条路堵死。

### 2. RWEverything 的 `RwDrv.sys`

驱动文件一落盘就被系统安全机制删除；GUI 的「安装驱动」对话框在无头环境点不了。
即使关了内存完整性，Win11 的驱动阻止列表仍会拦截。

### 3. WMI 接口

穷举后确认：

- 无 `Lenovo_FanMode` / `ThermalMode` / `LENOVO_GAMEZONE` 类
- `LENOVO_UTILITY_DATA` 只有 `GetIfSupportOrVersion` 方法，**没有 setter**

**结论：无法通过 WMI 脚本化切换风扇档位或性能模式。**

---

## 三、真正可用的通道：EnergyDrv

联想电脑管家底层通过 `Lenovo ACPI-Compliant Virtual Power Controller` 暴露的设备发命令。

### 设备名（需自动探测）

不同机型/驱动版本暴露的名字不同，依次尝试第一个能打开的：

```
\\.\EnergyDrv
\\.\Lenovo0
\\.\Lenovo1
\\.\AcpiVpc
```

⚠️ **设备只在联想电脑管家 / 联想实用程序运行时存在**（服务 `LenovoPcManagerService` / `LenovoTray` 在跑即可）。关掉管家 → `CreateFile` 直接失败。

### 两条 IOCTL

| 用途 | IOCTL | 入参 | 出参 |
|---|---|---|---|
| 控制 | `0x831020C0` | `{6, 1, mode}`，`mode=1` 最大 / `0` 正常 | 无 |
| 读状态 | `0x831020C4` | `{14}` | 一个 32 位值 |

均需 `GENERIC_WRITE` / `GENERIC_READ` 打开设备，**需管理员权限**。

### 状态读数方向（也踩过坑）

读索引 `14` 的返回值：

- 空闲态 ≈ **`0x85`**（133）
- 强制生效态 ≈ **`0x28`**（40）

早期把高低方向**判反了**（以为值越大越转），导致程序逻辑整体反过来。
正确判据：**`< 100` 且非 0 → 风扇在转**。

```csharp
bool IsFast() {
    uint v = ReadStatusRaw();
    return v != 0 && v < 100;
}
```

### 补充：读数存在过渡值，不能"切档后立刻读"

v1.1 加固时的实测发现：**切档后 EC 不会立刻反映新转速**。

在刚下发「最大档」后 250ms 读索引 14，有相当概率读到 **`0x87`(135)** —— 既不是空闲的
`0x85`(133)，也不是强制态的 `0x23`(35)，而是一个过渡值。3 次校准里有 2 次撞上了它，
由此算出的阈值会是「134、高值=在转」这种完全反向的判据。

更麻烦的是，若误信这个反向判据去控制，程序会把"正在满速"误判为"掉速"，于是每 600ms
做一次边沿重置（切正常档 300ms 再切回最大），**反而把满速打断**，实测保持率掉到 2/8。

正确做法：

1. 轮询读数直到「连续两次相同」才认为稳定（超时约 1.8s），不要固定 sleep 一次就读。
2. 把「最大档探针」改成边沿重置：`正常 → 等 300ms → 最大`。**空闲期直接下发最大档
   有时根本不生效**，必须先切回正常再切最大。
3. 校验两档读数差 ≥ max(8, 正常值×10%)，否则判为无效并重试。
4. 校准失败时**不要**依据读数做控制决策，只做周期性刷新 + 定期重排。

改造后连续 4 次运行：校准全部成功（`0x85`/`0x23` → 阈值 `84.0`），保持率均为 8/8。

## 四、9s + 2s 的固件周期

这是最关键的硬限制：

> EnergyDrv「启动除尘」的 **9 秒高速 + 2 秒暂停，是 EC 固件写死的周期，软件无法消除。**

能做的只有「缩短」，不是「消除」。尝试过的策略：

1. **高频刷新** —— 在高速相持续重发「最大档」命令，防止固件因无新命令而复位。
2. **边沿重置** —— 检测到掉速时，先发「正常档」→ 等 300ms → 再发「最大档」，等价于模拟一次程序重启，提升固件接受重触发的概率。
3. **定期兜底** —— 即使没检测到掉速，也每约 30 秒无条件做一次边沿重置，抢在固件会话结束前重排。

最终 C# 实现参数：

```csharp
LoopIntervalMs      = 600;   // 循环间隔 < 2s，比固件暂停更快
EdgeGapMs           = 300;   // 边沿间隔
ForceEdgeEveryLoops = 50;    // ≈30s 无条件兜底重置
ArmIdleThreshold    = 100;   // 读数 <100 判为在转
```

效果：风扇**绝大部分时间**保持满速，但**不可能做到严格零间隙**。

---

## 五、想要真正零间隙怎么办

只能用**固件层面的意图**：手动开启联想「性能模式」（`Fn+Q` 或电脑管家）。
那是固件自己指定的连续最大档，不经过除尘命令，因此没有 9+2 周期。

---

## 六、第三方工具能否读到真实转速

用 LibreHardwareMonitor（`src/lhm_spike/`）验证过：**读不到可信的真实转速**。
这也解释了为什么本项目只能靠 EnergyDrv 的状态读数间接判断「是否在转」，而无法直接读取 RPM 并做闭环控制。
